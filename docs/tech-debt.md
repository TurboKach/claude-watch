## Disk scanner: `du` stderr taint-matching does not converge (P2, deferred 2026-08-19)

**Where:** `tools/disk-scan.sh`, the stderr-attribution block that classifies each `du` diagnostic line as belonging to a group, `RESIDUAL` (harmless/unattributable), or `FATAL` (wholesale-taint every sweep-fed group) — `:634-652` at HEAD `8462e0a`, plus the coverage-count consumer at `:690` and `tools/advise-disk.sh:517-518`.

**Root cause.** The scanner infers what `du` actually measured by string-matching the *text* of its stderr output, not by observing `du`'s traversal directly. Across three `/codex challenge` rounds this mechanism has flipped between over-tainting and under-tainting and never settled:

- **Round 1** (`edc0b69`): any stderr line with no recoverable absolute path — including a legitimate `du: fts_read: ...` pathless fatal diagnostic — was mapped to harmless `RESIDUAL`. A real traversal abort was reported as if nothing happened. *Under-taint.*
- **Round 2** (`7d22a0d`): fixed by special-casing `fts_open`/`fts_read` to `FATAL` (wholesale-taint). This over-tainted: a directory literally named `foo\nfts_read` produces a stderr continuation line that strips to exactly `fts_read`, and one pathological filename now mutes every group in the sweep. *Over-taint.*
- **Round 3** found round 2's fix still incomplete in the other direction: the fatal-diagnostic set is `fts_open`/`fts_read` only. Other real fatal `du` diagnostics — `du: stdout: ...` write failures, "No memory for hardlink detection", directory-hardlink allocation failures, and the symlink-cycle exits present in Apple's `du.c` — still fall through to harmless `RESIDUAL`. *Under-taint, again, for a different diagnostic shape.*

Round 3 also found the symlink recheck immediately downstream shares the same category of problem for a different reason (below). Codex's verdict: **not converged** — patching the matcher a fourth time is expected to reproduce one of the two failure shapes again, just for a new diagnostic string.

**Why deferred.** The structural alternative — measure divergence per kind-table entry instead of inferring it from one shared sweep's stderr text — is exactly what the current single-sweep design was introduced to avoid. A full `du -kxd 4 $HOME` sweep measured 62-64s against the scanner's 120s deadline (see `docs/prompts/disk-scanner-coverage-plan.md`, "Measured cost of 'look everywhere'"); per-entry measurement multiplies that cost by the entry count. Fixing this properly is a design change, not a matcher patch, and was out of scope for the P1 fix this was found alongside.

**Symptoms filed under this root cause:**

1. **fts_read false-positive wholesale taint** — `disk-scan.sh:642-645`. A real, accessible file or directory named so that `du`'s stderr continuation line strips to exactly `fts_read` (or `fts_open`) triggers `FATAL` and taints every sweep-fed group, even though nothing about the sweep actually failed to complete. *Over-taint.*
2. **Fatal-diagnostic set too narrow** — `disk-scan.sh:633,669`. Other genuinely fatal, pathless `du` diagnostics (write failures, hardlink allocation failures, symlink-cycle exits) are not in the `FATAL` set and fall through to `RESIDUAL`, so a real traversal abort reports `affected=0` on groups it never finished measuring. *Under-taint.*
3. **Post-sweep symlink recheck is TOCTOU** — `disk-scan.sh:548,562`. The recheck inspects each kind-table entry's canonical path *after* `du` has already run, and infers what `du` traversed from that final state. Two failure shapes coexist: a directory that was a symlink *during* `du` but is a directory again by recheck time passes silently even though `du` physically skipped it (*under-taint*); a directory that was correct throughout `du` but becomes a symlink immediately afterward is discarded as if the measurement never happened (*over-taint*). Checking final pathname state cannot prove what object `du` actually walked at the moment it walked it — a TOCTOU window around `du`'s own execution, not something a smarter check-timing can close without observing the traversal itself.
4. **Coverage count mislabels its own cause** — `disk-scan.sh:690`, `tools/advise-disk.sh:517-518`. When a sweep is marked incomplete but the stderr-driven residual count came up empty (an `fts_open`/`fts_read` abort, a silent nonzero `du` exit, or a missing `$HOME` row in `$sout`), the scanner forces `ucount=1` as a placeholder so the coverage note has a nonzero count to report. The analyzer then always describes that number as "paths it could not attribute to a group" (`advise-disk.sh:518`). For a traversal abort, no such path count was ever measured — the `1` is a synthetic "at least one reason exists" flag, and the message asserts a specific, false diagnosis of what went wrong.

**What would need to be true to fix it.** A design decision on whether to keep the single-sweep-plus-stderr-parsing approach (and enumerate + handle the closed set of `du.c`'s fatal pathless diagnostics, accepting that "closed set" claim needs re-verification against every `du` build these scripts might run under) or move to per-entry measurement with a cost model that fits the existing 120s deadline (e.g. sweep first, then re-measure only entries the sweep's own row count/coverage signals as suspect). Either path needs the disk-scan fixture harness able to fabricate `du` stderr/exit-code shapes and newline-containing filenames, which — see the caveat below — has not actually been exercised yet for this codepath.

## Disk scanner: untrusted parsing of `du`'s raw output (P2, deferred 2026-08-19)

**Where:** `tools/disk-scan.sh:578` (the T/H-row conversion awk that emits records from `du`'s raw output), merged into group totals with no group ever marked affected at `tools/disk-scan.sh:835` (`tot[g] += $3 + 0; cnt[g]++`, in the cache-assembly awk). This second location was `:824` at the `7d22a0d` round-3 review point; it moved to `:835` at HEAD `8462e0a` because an unrelated P1 fix (round-3 finding 1, `$HOME`-scope of the `attributed` cover figure) inserted lines earlier in the same function.

**What's wrong.** `du`'s raw output is newline-delimited `size<TAB>path` records, parsed as trusted input with no validation of field count or that the path is representable on one line. A directory at depth ≤ `$MAXDEPTH` named so that its `du` line reads as `x\n999999<TAB>$HOME/Downloads` (i.e. a crafted trailing segment that, once `du` emits it, looks like a second complete `size<TAB>path` record matching an existing kind-table entry) injects an attacker-chosen size `H` measurement for that entry. This forged row is summed into the group total exactly like a real one, with `affected=0` — the corruption enters the cache as clean, trusted data. *Under-taint*: this is not caught by the taint mechanism above at all, because the forged line is syntactically well-formed.

**Why deferred.** Requires directory names containing raw newlines, which is an unusual local-filesystem attack surface (this tool runs against the operator's own `$HOME`, not attacker-controlled input) — assessed as P2, not urgent enough to hold the P1 fix. Also static-analysis-only (see caveat below); the actual forging behavior of `du`'s line-based output under this exact awk parser has not been executed and confirmed.

**What would need to be true to fix it.** Switch the sweep to a record separator `du`/awk can't collide with (NUL-delimited output isn't offered by `du -k`; the alternative is validating each parsed record against the kind-table's known path set before trusting its size, or driving the sweep through `find -print0` + per-entry `du` instead of parsing one shared multi-line `du` stream — which is the same per-entry-measurement tradeoff discussed in the taint-convergence entry above).

## Disk scanner: symlink-recheck failure can be double-counted in `coverage_incomplete` (P2, deferred 2026-08-19)

**Where:** `tools/disk-scan.sh:566` (recheck removes the entry and increments `ucount`) and `tools/disk-scan.sh:634,659` (stderr attribution, run afterward against the already-filtered entry table, increments `ucount` again).

**What's wrong.** If a kind-table entry fails the post-sweep symlink recheck, it's dropped from `$WORK/entries` and `ucount` is incremented (`:566-570`). The stderr-attribution pass that follows (`:634-652`) then runs against that same, already-filtered table — so if `du`'s stderr also names that now-removed entry (e.g. a permission-denied line for the same path), it can't match any surviving table row, falls into `RESIDUAL` (`:646`), and increments `ucount` a second time (`:659-660`) for what is a single underlying failure. No group is double-affected (`affect()` itself is idempotent per group), but the `coverage_incomplete` note's count can overstate how many distinct paths went unmeasured.

**Why deferred.** Cosmetic relative to the P1 fixed alongside it — the note already says "coverage incomplete, re-run"; an inflated count doesn't change the recommended action, only the number in the sentence. Static-analysis-only finding (see caveat below).

**What would need to be true to fix it.** Track removed-during-recheck paths in a set, and skip incrementing `ucount` in the stderr-attribution pass when a `RESIDUAL` line's path matches an already-counted removal — or compute `ucount` once, after both passes, over the union of (recheck removals) and (unattributed stderr lines) rather than as two independently-incrementing counters.
